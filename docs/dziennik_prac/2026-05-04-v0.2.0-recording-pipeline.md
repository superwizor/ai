# Sesja: 🎉 Kamień Milowy v0.2.0 — End-to-End Recording Pipeline

**Data:** 2026-05-04 (sesja trwała od 03.05 do 04.05, ~8h)  
**Tag:** `v0.2.0`  
**Cel sesji:** Uruchomienie pełnego pipeline'u nagrywania sesji terapeutycznej — od kliknięcia „Nagraj" w aplikacji Flutter, przez szyfrowanie i przesyłanie audio, aż do zapisania sesji w bazie danych Cloud SQL i pliku w GCS.

## ✅ Osiągnięcia — Co Działa End-to-End

### 1. Autentykacja i Zarządzanie Użytkownikami
- **Firebase Auth** → tokeny ID propagowane przez gRPC `AuthInterceptor`
- **Auto-registration:** przy pierwszym logowaniu użytkownik jest automatycznie tworzony w `identity-svc` (tabela `users` w Cloud SQL)
- Dane użytkownika i pacjentów **persystują** między restartami aplikacji

### 2. Zarządzanie Pacjentami
- Tworzenie nowych pacjentów (imię, nazwisko)
- Lista pacjentów ładowana z backendu (`clinical-svc`) przy starcie
- Pacjenci przypisani do terapeuty (`therapist_id` z tokenu Firebase)

### 3. Nagrywanie Audio z Wizualizacją
- **EuphireWaveformIndicator** — nowy komponent z real-time wizualizacją amplitudy mikrofonu
- Szyfrowanie chunk'ów w locie (session key)
- Nagrywanie w tle z timer'em i kontrolkami start/stop

### 4. Upload do GCS przez Signed URLs
- `ingestion-svc` generuje podpisane URL-e (GCS Signed URLs)
- Chunk'i audio uploadowane bezpośrednio do bucketu `superwizor-ai-25ecd-audio-uploads`
- Sesja tworzona w bazie po zakończeniu uploadu

### 5. Infrastruktura Cloud Run
- **ingestion-svc** zdeployowany na Cloud Run (europe-central2)
- `min-instances=1` eliminujący cold start
- gRPC health check zaimplementowany
- `roles/iam.serviceAccountTokenCreator` dla signed URL generation

## 🏗 Architektura i Decyzje

### Routing gRPC — Dedykowane Endpointy
**Decyzja:** Odszliśmy od routowania przez `api-service` (który był placeholder'em HTTP) na rzecz bezpośrednich połączeń gRPC do dedykowanych serwisów:
- `identity-svc` → uwierzytelnienie + profil
- `clinical-svc` → pacjenci + sesje + raporty  
- `ingestion-svc` → upload audio + signed URLs

**Uzasadnienie:** `api-service` to był prosty "Hello World" HTTP handler. Próba routowania gRPC przez niego generowała 502 Bad Gateway.

### IAM — Service Account Token Creator
**Decyzja:** Nadanie `roles/iam.serviceAccountTokenCreator` default compute SA.  
**Uzasadnienie:** `ingestion-svc` musi podpisywać URL-e GCS (`iam.serviceAccounts.signBlob`). Bez tej roli → 403 Permission Denied.

### Cold Start Mitigation
**Decyzja:** `min-instances=1` na ingestion-svc.  
**Uzasadnienie:** gRPC z klienta Flutter miał timeout 10s. Cloud Run cold start to ~15-25s. Zwiększono timeout do 30s + min-instances.

### Bezpieczeństwo (Zero Data Loss, Zero PII)
- ✅ Token Firebase propagowany przez `AuthInterceptor` do każdego gRPC call
- ✅ Signed URLs z krótkim TTL (15 min) — brak bezpośredniego dostępu do bucketu
- ✅ `therapist_id` wyciągany z tokenu (nie od klienta) → zapobiega unauthorized access
- 🔶 Szyfrowanie transkryptów (envelope encryption) przygotowane w `stt-worker` ale z placeholder DEK — do wymiany na Cloud KMS w Fazie 3

- [ ] **Placeholder DEK w stt-worker** — `ENCRYPT_PLACEHOLDER` zamiast prawdziwego Cloud KMS envelope encryption
